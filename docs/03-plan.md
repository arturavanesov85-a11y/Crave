# 03. План реализации

Каждая часть заканчивается рабочим результатом с тестами. Порядок построен так, чтобы самые рискованные механизмы — бронирование, расчёт, права, финансы — были готовы и проверены до интерфейсов.

## Этап 0. Фундамент

1. Каркас монорепозитория: `apps/{rental,sales,service,crm,api}`, `packages/{ui,pricing,db,contracts,config}`, TypeScript, ESLint, Prettier, Vitest.
2. `infra/docker-compose.yml`: PostgreSQL 16, MinIO, Mailpit. `.env.example`.
3. CI: проверка типов, линтер, тесты (unit + интеграционные с реальной PostgreSQL).

**Готово, когда:** `npm run dev` поднимает API и пустые приложения; `npm test` зелёный в CI.

## Этап 1. Ядро (без интерфейса)

Порядок — по критичности.

| # | Часть | Ключевые тесты |
|---|---|---|
| 1.1 | Схема БД, миграции, сид из `docs/data/current-site-tariffs.json` (с пометкой «требует проверки») | миграции применяются и откатываются |
| 1.2 | `packages/pricing` + `POST /public/quote` | таблица случаев: границы ступеней (2/3, 6/7, 13/14, 29/30 сут), округление, пробег, услуги, скидка, залог вне итога, копейки |
| 1.3 | `booking`: доступность, hold, подтверждение, продление, блокировки ТО | **параллельный тест**: N одновременных запросов на один слот → ровно 1 успех; соседние брони с буфером; истёкший hold не блокирует; продление упирается в следующую бронь |
| 1.4 | `orders`: статусы и переходы, снимок условий, замена машины, отмена, неявка | все недопустимые переходы отклоняются; смена тарифа не меняет `terms_snapshot` |
| 1.5 | `identity`: пользователи, роли, разрешения, направление | матрица «роль × эндпоинт»: сотрудник сервиса не получает заказы проката, сотрудник выдачи — только назначенные, тех. админ — без документов клиентов |
| 1.6 | `finance`: журнал, сторно, залоги, удержания с подтверждением | `UPDATE/DELETE` журнала невозможны; удержание без права отклоняется; залог не попадает в выручку; повторное платёжное событие с тем же ключом не дублируется |
| 1.7 | `leads`: приём с сайтов, идемпотентность, антиспам, UTM | двойная отправка формы → 1 обращение |

**Готово, когда:** все критерии приёмки, касающиеся логики (бронирование, расчёт, права, финансы), проверяются автотестами.

## Этап 2. Дизайн-система и сайт проката

1. `packages/ui`: токены из аудита, типографика Montserrat / Cormorant Garamond, кнопки, поля, выбор дат, карточка автомобиля, `DirectionSwitcher`.
2. Сайт проката: главная с выбором дат на первом экране, автопарк с фильтрами, карточка машины с калькулятором, цены (режимы «Рассчитать» и «Все тарифы», мобильные карточки вместо таблицы), условия, контакты, подтверждение заявки.
3. SEO: метаданные, `sitemap.xml`, микроразметка, 301-перенаправления со старых адресов (`/prajs/` → `/ceny/` или сохранение адреса — решить).
4. Яндекс.Метрика с тем же счётчиком, цели на отправку форм.

**Готово, когда:** Lighthouse mobile ≥ 90 по производительности и доступности; заявка с сайта появляется в CRM ровно один раз.

## Этап 3. CRM проката

Порядок — от экранов, которые нужны каждый день.

1. Вход, профиль, переключатель направления.
2. Календарь автомобилей (день/неделя/месяц), создание брони из свободного интервала, перенос с подтверждением.
3. Карточка заказа: шапка + вкладки «Условия», «Оплаты», «Выдача и возврат», «Документы», «История».
4. «Сегодня»: выдачи, возвраты, просрочки, новые заявки, подготовка, просроченные оплаты и залоги.
5. Мобильная форма осмотра: пробег, топливо, чек-лист, фото, повреждения (с отображением открытых).
6. Автопарк: карточка машины, документы со сроками, ТО, история.
7. Клиенты с ограничением видимости по направлению.
8. Финансы: операции, сторно, отчёты; экспорт по разрешению.
9. Уведомления в CRM + адаптеры каналов в тестовом режиме.

## Этап 4. Сайты автосалона и сервиса

Минимальные сайты на той же дизайн-системе: главная, формы обращений, контакты, пустые состояния каталога и перечня услуг до получения реальных данных. В CRM — разделы входящих обращений.

## Этап 5. Подготовка запуска

1. Нагрузочный и параллельный прогон бронирования на staging.
2. Проверка прав: прямые запросы к API под каждой ролью.
3. Перенос данных: машины, фото, тарифы (после подтверждения владельцем), карта перенаправлений.
4. Инструкции: развёртывание, резервное копирование, проверка восстановления, откат на WordPress.
5. Переключение DNS только после приёмки; WordPress остаётся в резерве на поддомене до окончания периода наблюдения.

## Вне первой версии

Онлайн-эквайринг, телефония, мессенджеры, GPS, склад и заказ-наряды сервиса, сделки продажи, бухгалтерские интеграции, онлайн-подтверждение брони без менеджера.
